# GPS coordinate configuration — self-hosting guidance

Verified against HEAD db64018 and live state on 2026-10-06 18:12Z / 14:12 ET.

## The short version

If you run the platform against a real ADS-B receiver (UltraFeeder/readsb),
set the receiver's real coordinates before going live, in two places:

1. **Application layer** — `ULTRAFEEDER_LAT` / `ULTRAFEEDER_LON`. Keep the
   value in `/etc/corporatetraveldc/dispatch-secrets.env`; it reaches the
   containers that read it through the scoped env files generated by
   `scripts/service-env/generate.py --write`
   (`/etc/corporatetraveldc/svc/{ingest,poller,runner,web}.env` — the four
   allowlists that list it). Consumers: `ingest/local_airspace.py`
   (`RECEIVER_LAT/LON`), `runner/main.py` (`DEFAULT_LAT/LON`),
   `web/main.py` (`_ADSB_DEFAULT_LAT/LON`).
2. **Receiver layer** — `READSB_LAT`, `READSB_LON`, `READSB_ALT`,
   `TAR1090_DEFAULTCENTERLAT`, `TAR1090_DEFAULTCENTERLON` in
   `/etc/corporatetraveldc/ultrafeeder-secrets.env` (0600, template
   `config/ultrafeeder-secrets.env.example`), loaded only by
   `.config/containers/systemd/corporatetraveldc-ultrafeeder.container`.

`config/dispatch.env.example` also carries `ULTRAFEEDER_LAT` /
`ULTRAFEEDER_LON` placeholders; the live `dispatch.env` does not set them
(count 0 at 18:12Z) — the secrets file is the one in use.

Left unset, everything still runs on hard-coded DC-area placeholder
defaults in the three modules above, but:

- distances, the compass-quadrant summary and the map's range rings are
  wrong for your site;
- the globe.airplanes.live embed's "H"/home key and distance columns are
  wrong;
- MLAT accuracy depends on the receiver's site position being correct
  (readsb uses it as a fixed reference);
- feeder registrations carry the wrong location (ultrafeeder's
  `ULTRAFEEDER_CONFIG` feeds FlightAware, FR24, ADSBHub, airplanes.live and
  OpenSky MLAT; PlaneFinder and AirNav Radar run as their own containers).

## Why two settings

`ULTRAFEEDER_*` drives the application (distances, alerts, the runner UI).
`READSB_*` / `TAR1090_*` drive the receiver (readsb MLAT, tar1090's
`receiver.json`). Different processes read them at different times;
setting one does not set the other. They must agree.

## The frontend's single source

`GET /api/v1/frontend-config` (`src/runner/main.py`) returns
`receiver_lat` / `receiver_lon` from `DEFAULT_LAT` / `DEFAULT_LON`.
`src/runner/frontend/src/hooks/useReceiverLocation.js` is the one hook that
fetches it; map and compass components use that hook. **Never hard-code a
coordinate in a `.jsx`/`.js` file**: the public mirror's
`scripts/scrub-public-tree.py` substitutes only literals it already knows
and cannot catch a new one.

## Why the "H" button specifically

tar1090 keys its "H"/home button and distance columns off `SiteLat` /
`SiteLon`, not `centerlat` / `centerlon` (which only move the initial
camera). Without `SiteLat/SiteLon` it uses whatever browser geolocation it
cached in that origin's `localStorage`.
`src/runner/frontend/src/components/MapView.jsx` sends `SiteLat`,
`SiteLon` and `SiteClear=1` on every embed load. For a local tar1090
opened directly, append `?SiteClear=1` once to purge a stale cached home.

## Incident this codified (2026-08-24)

Four places disagreed about the receiver location (the app value, a stale
receiver value, and two literals in `MapView.jsx` and
`useCompassSummary.js`), and the embed set only `centerlat/centerlon`, so
the "H" button showed a browser-cached location until the embed URL was
fixed. The receiver values moved to the scoped `ultrafeeder-secrets.env`
on 2026-08-26 (review finding C-4).
